## How this was run


The console end-to-end test is the only path that builds a real artifact chain,
so its outputs are the run's evidence: a 72-record dataset (`8,782` tokens,
released through a two-person gate), a tokenizer with a 600-token vocabulary, an
80-step contrastive run (loss `3.91 → 1.49`, grad norm `141 → 10.5`, ~4,000
tokens/s on CPU, `$0.0017`), a frozen 16-item eval set, a passing report
(`recall@10 0.25` against BM25 `0.1875`; `mrr 0.189` against `0.050`), promotion
through a two-person gate, and 44 audit events chained in that run. Everything
in that sentence is measured; none of it is proof of quality at any real scale.

## Findings that matter more than the score

1. **The checklist tests a pretraining programme; the product is a control plane
   plus two small tracks.** The from-scratch track trains an **encoder** for
   embeddings and a classifier head (`training/model.py`, `training/classifier.py`).
   The only generative path is the alpha track: a streamed LoRA on the query
   projection of a pinned `Qwen3-4B`, not instruction tuning. So the items that
   assume a decoder run, a next-token loss near `ln(vocab)`, SFT/DPO, public
   benchmarks and a 32k context are not small omissions — they are a different
   product. Roughly twenty P0/P1 items fall into that group.
2. **One P0 check is a rubber stamp.** `E-09 permission_leak` is emitted by
   `evals/harness.py` as `{"passed": True, "note": "permission enforcement is
   verified by the retrieval service tests"}`. The retrieval service does enforce
   ACLs, and `test_retrieval_enforces_document_permissions` proves it, but the
   eval report itself cannot fail this check. A report that cannot fail is not
   evidence.
3. **Token budget was estimated, not measured.** At build time `token_count` is
   `len(text)//4`, because no tokenizer exists yet. **Amended:** once the
   tokenizer is trained the count is measured exactly, the dataset says which
   count it holds, and each run records tokens per parameter against the
   20-token floor (`D-05`).
4. **Correction — the release audit does scan for secrets.** My first read of
   `pii_spot_check` said otherwise. Every kind in `SECRET_PATTERNS` is also in
   `PII_PATTERNS`, and ten of those kinds, including keys, tokens, passwords and
   connection strings, are in `CRITICAL_DETECTORS`. A surviving secret blocks a
   release today; `test_the_release_audit_refuses_a_surviving_api_token` now
   proves it. The finding was wrong and is withdrawn.
5. **The training stack is one process on one machine.** No sharded tokenized
   corpus (`D-17`), no mixed precision or FlashAttention (`S-03`), no
   parallelism (`S-02`), no cluster backend exercised (`C-06`), no node health
   handling (`C-07`), no automatic restart (`S-06`).
6. **Post-training does not exist.** There is no SFT set, no preference tuning,
   no safety-behaviour suite, no regression-on-every-candidate suite. Section 8
   is empty.
7. **What is genuinely strong is the guardrail layer**, and it is stronger than
   most of this checklist assumes: hash-chained audit, eight gate types with
   recorded approvers and dual control, five budget scopes with a mid-run cost
   cap, a kill switch, least-privilege role matrix, network-denied sandbox,
   offline-by-default egress, write-protected frozen eval sets, permission-aware
   retrieval, and the documented rule that neither the from-scratch track nor a
   released dataset can be edited.

## Amendments after the run

The same day, four items were closed and one verdict was corrected. Each has a
test in `tests/test_acceptance_holes.py`.

- `data/pipeline.py` gained `measure_token_count`: after the tokenizer is trained
  the dataset's count is the tokenizer's own count, `stats.token_count_kind`
  says `measured` or `estimate`, and the page says which. `trainer.py` records
  `token_budget` (tokens, parameters, tokens per parameter, floor, whether it
  meets it) on every run and audits `train.token_budget_short` when it does not.
  **D-05 PASS**.
- `evals/harness.py` no longer passes contamination when it could not run: with
  no training corpus and a labelled eval set, the check fails and says why.
  **E-06 PASS**.
- The `permission_leak` check is now `permission_probe`, using the serving
  layer's own `Principal.can_read`. It fails on a labelled document with no
  access list, on one a stranger can read, and on one nobody can read.
  **E-09 PASS**.
- The release refusal now says "release audit ... personal data or a secret"
  rather than "PII audit", and a planted API token is proven to block a release.
  D-14 was already passing; the wording and the test are the only change.

A second amendment closed the four proofs the checklist asks for as tests:

- **M-06 overfit** is now a product check: `training/overfit.py` trains a tiny
  batch of eight lines until it is memorised and records the ratio; run on this
  machine it takes 3.3s and moves the loss from 4.17 to 0.007. The Models page
  offers it as "Check the training code learns" for anyone with `train_model`,
  and the refusal for anyone without is audited. **M-06 PASS.**
- **S-04 resume was dead code.** `Trainer.train` minted a new run id on every
  call, so its checkpoint directory was always empty and `resume=True` never
  found a file. It now accepts a run id, resumes from that run's checkpoint and
  reports `resumed_from`; the test kills a 4-step run and continues it to 8 from
  step 4. **S-04 PASS.**
- **S-07 reproducibility** is proven: two runs of the same config, dataset and
  seed produce identical loss curves. **S-07 PASS.**
- **D-19 lineage** is now checkable, not just claimed: `sample_lineage` traces a
  sorted sample of records to the source entries, content hashes, config hash and
  code commit the dataset recorded, and the dataset page shows the result. The
  commit lookup falls back to the package directory, so a build run from a
  temporary data directory still records the code that produced it. **D-19 PASS.**

A third amendment gave the checklist's Foundations section a record instead of
prose, in `internal_ai/brief.py` and `/console/brief` (tests in
`tests/test_project_brief.py`):

- One `project_brief` record holds the target, quality bar, languages, context
  length, up to three success metrics with a direction and a threshold, budget,
  timeline, deployment, latency target, data restrictions, non-goals and a named
  owner for each of `ml_lead`, `data_engineer`, `infra`, `evaluation` and
  `security`. Saving needs `write_brief` (program lead or ML lead), is audited as
  `brief.updated` with the gaps still open, and is refused to anyone else.
- `ProjectBrief.missing` names what is still unrecorded in the words the
  checklist uses, and it is shown where the work starts: a card on the overview
  with the target, the metric and its threshold and the owners, and a callout on
  the plan page while the brief is incomplete. **F-01, F-02, F-03, F-05 PASS.**

These four pass as *records the company keeps and the platform checks for
completeness*, not as facts the platform can verify: it cannot know whether 0.70
recall is ambitious, only that a number and an owner exist.

An evaluation now reads the brief instead of ignoring it: every metric the brief
records is matched to the run's metric by name (`recall@10` and `recall_at_10`
are the same metric), its threshold parsed (`0.70`, `70%`, `≥ 0.7` are the same
bar), and the report's `brief_targets` check records each target as met,
missed or unmeasured. A missed or unmeasurable target fails the report, so the
promotion gate cannot approve a model the brief says is not good enough, and the
notes and the advice name the gap: "recall@10 at least 0.70 — measured 0.412,
below the bar". The classifier path is judged the same way: its accuracy is
compared with the brief, a miss turns its decision to a fail and is named in its
notes, and the classifier run row shows the same per-target lines as an encoder
card. A model card lists its last five evaluations ("recall@10 0.655 of 0.70 —
0.045 short", newest last), so progress toward a target is visible without
opening each report. Each row is read against the bar that report recorded at
the time, so editing the brief does not rewrite how short a past run was: the
row says "the brief now asks 0.90" instead. Reports from before the brief was
read at all fall back to today's bar and are marked "(the brief today)". A brief
with no metric adds no check at all. The suite is 251 tests after these, all
passing, and `ruff` is clean.

## What is actually required, in order

**1. Decide the bar (blocks everything else).** If the product must satisfy this
checklist itself, then the missing item is a *pretraining track*: a decoder run,
token shards, mixed precision, validation during training, SFT and preference
tuning. If the product must make a company's from-scratch project run well, then
the missing item is *records and proofs*: target, metrics, licence, token
budget, sampled audits, resume and reproducibility tests, a real permission-leak
probe. The first is a quarter of work; the second is days.

**2. Close the P0s that are cheap and honest.** Done for eight of them: a real
token count, contamination that fails closed, a permission probe that can fail,
a secret scan proven at release, the overfit check, resume (which was dead
code), the two-run reproducibility proof and the sampled lineage trace. What
remains is mostly scope or records rather than engineering: SFT, scale, the
project brief, a sample outage audit and the data-loader offset.

**3. Add the five evidence records the checklist asks a company for** — target,
metrics, constraints, staffing, run-health sign-off — as first-class objects the
plan and the gates read. This is what turns the tool from "a pipeline" into "a
programme a bank can hand an auditor".

**4. Post-training and scale are separate projects.** Say so out loud in
`PRODUCT.md`, or the checklist will keep reading as a failed product rather than
a deliberately narrow one.

## The question this run cannot answer

The checklist and the product disagree about what "from scratch" means. Which
one should change: does the product owe a generative pretraining run, or does
the checklist owe an acknowledgement that the product's from-scratch track is a
small encoder and the only generator is the alpha adapter on a pinned base?
